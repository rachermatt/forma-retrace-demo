# Forma ReTrace APS verification

Updated November 4, 2026. This document separates documented contracts, implementation tests, and live authorization. The historical credential-only probe below has not been repeated or expanded into a customer-project demonstration. The original handoff remains source material; the current product name is **Forma ReTrace**.

## Implemented boundary

`server/aps.ts` implements a server-managed authorization-code flow for the supplied **Traditional Web App**, refresh, local logout and read-only project access. The new `server/aps-models.ts` adapter extends it to authorized folders, model items, exact versions, derivative metadata and property snapshots. Only `data:read` is requested. The default local callback remains `http://localhost:8080/`, matching the user-provided app registration; a configured callback must match its APS registration. Credentials come from server environment variables and never enter the browser bundle.

| Operation | Official APS contract | Local behavior |
|---|---|---|
| Consent | `GET /authentication/v2/authorize` | Sends the browser to Autodesk with a random state bound to an HttpOnly browser cookie. |
| Code exchange | `POST /authentication/v2/token` | Confidential client authentication through HTTP Basic; authorization code and exact redirect URI in the form body. |
| Refresh | `POST /authentication/v2/token` | Uses `grant_type=refresh_token`, current refresh token and `data:read`; retains the latest returned token. |
| Projects | `GET /project/v1/hubs/{hub_id}/projects` | Fixed configured hub, authenticated user context, GET only, follows validated pagination. |
| Top folders | `GET /project/v1/hubs/{hub_id}/projects/{project_id}/topFolders` | Rechecks membership in the configured hub before granting folder navigation. |
| Folder contents | `GET /data/v1/projects/{project_id}/folders/{folder_id}/contents` | Folder must have been obtained through that session's authorized source browser. |
| Model versions | `GET /data/v1/projects/{project_id}/items/{item_id}/versions` and `GET /data/v1/projects/{project_id}/versions/{version_id}` | Item must be browsed first; rereads exact version and verifies its parent item before extraction/import. |
| Model metadata | `GET /modelderivative/v2/designdata/{urn}/manifest`, `/metadata` and `/metadata/{guid}/properties?forceget=true` | URN comes from the selected source version, never an arbitrary browser URL/URN. Requires a ready derivative and a 3D viewable returned for that version. |

The official [hubs-browser tutorial](https://get-started.aps.autodesk.com/tutorials/hubs-browser/data), [top-folder reference](https://aps.autodesk.com/en/docs/data/v2/reference/http/hubs-hub_id-projects-project_id-topFolders-GET/), [folder-contents reference](https://aps.autodesk.com/en/docs/data/v2/reference/http/projects-project_id-folders-folder_id-contents-GET/), [item-versions reference](https://aps.autodesk.com/en/docs/data/v2/reference/http/projects-project_id-items-item_id-versions-GET/) and [Model Derivative properties reference](https://aps.autodesk.com/en/docs/model-derivative/v2/reference/http/urn-metadata-guid-properties-GET/) were checked for the new adapter. Dynamic reference bodies were not fully exposed by the research browser; the official tutorial and SDK examples support the hierarchy, while exact live behavior remains a qualification gate.

In **Model Data & Metrics**, choose **Private imported property extracts**, then **Sources & imports**; live mode offers this browser. A property extract stays server-side behind a ten-minute, session-bound receipt; import rechecks access before storing a trusted APS-origin snapshot. The raw-JSON import route cannot assert APS provenance. Snapshots retain exact project/model/version and derivative/viewable references, extraction time and source external IDs where available. Missing external IDs are explicitly marked as version/viewable object IDs. Units and geometry absent from the response are not invented. Metadata import does not change historical evidence associations or verify an As-Built/For-Record designation.

Autodesk documents the confidential client authorization-code flow and its Basic-authenticated token exchange in the [3-legged authorization tutorial](https://aps.autodesk.com/en/docs/oauth/v2/tutorials/get-3-legged-token). Its [OAuth v2 migration guide](https://aps.autodesk.com/blog/migration-guide-oauth2-v1-v2) gives the refresh request format. APS documents PKCE as the public-client variant in its [PKCE tutorial](https://aps.autodesk.com/en/docs/oauth/v2/tutorials/get-3-legged-token-pkce/get-3-legged-token-pkce/). This implementation follows the documented confidential flow for the provided app type; it does not assume an unverified confidential-client/PKCE combination.

Configure your intended Forma hub UUID through `APS_HUB_ID`. The Data Management adapter uses its `b.`-prefixed representation, following the documented [Forma-to-Data-Management hub ID conversion](https://aps.autodesk.com/en/docs/data/v2/reference/http/hubs-GET). The original installation's supplied hub was not established to be a project-bearing customer hub. A Developer Hub used to manage applications must not be assumed to contain the intended project data. Installation-specific identifiers are not required for the synthetic demo.

The [project endpoint reference](https://aps.autodesk.com/en/docs/data/v2/reference/http/hubs-hub_id-projects-GET) and [pagination guide](https://aps.autodesk.com/en/docs/data/v2/developers_guide/pagination) are the intended endpoint contracts. These pages were located, but their dynamic reference bodies were not exposed by the research browser. The official [Data Management changelog](https://aps.autodesk.com/en/docs/data/v2/change_history) confirms `page[number]` and `page[limit]` support, and the official [project browsing tutorial](https://get-started.aps.autodesk.com/tutorials/acc-issues/data) confirms the project list is limited to the signed-in user's membership. Exact live paging behavior still needs an authorized-project exercise.

## Controls implemented and tested locally

Opaque sessions and access/refresh tokens live only in server memory, separately for each browser session. Restarting the server signs out all browsers. States expire after ten minutes and are consumed before code exchange; sessions expire after eight hours. Local logout deletes the tokens held by this process. It does not revoke Autodesk consent or end the user's Autodesk browser session.

Only the configured hub path is available through the adapter. Pagination cannot redirect bearer tokens to another origin, another hub, or an unrelated endpoint. HTTP redirects are refused. Repeated/cyclic pages and more than 100 pages fail without returning a partial list. The app refreshes shortly before expiry, serializes concurrent refreshes, and retries a resource 401 once. A 403 reports denied permissions without declaring authentication failed. Upstream body text, tokens, and client credentials are excluded from public errors/status.

Model-resource bodies are bounded at 30 MiB; an extract is limited to 10,000 elements and 498 source properties per element, reserving two fields for identifier provenance. Unsupported oversized, empty, ambiguous or colliding extracts fail explicitly; no partial dataset or silently truncated property set is offered. Browsing grants and extract receipts are scoped to the signed-in session and removed by logout. Fixture mode and the public synthetic deployment cannot read APS model sources. The parent application routes enforce local sessions and CSRF protection for extraction/import mutations.

Run `node --test tests/aps.test.ts tests/aps-models.test.ts` from the project directory. **29 tests passed** using mocked fetch responses: the original 18 OAuth/project tests and 11 model-source tests. They cover disabled fixture access, missing config, callback and hub validation, minimal scopes, one-use browser-bound state, expiry/replay, token privacy, malformed token/project responses, isolated sessions, logout during refresh, refresh rotation/concurrency, fixed-hub reads, empty-page pagination, unsafe next links, cycles, permission denial, 401 retry, network errors and redirects. Source checks additionally cover authorized browse ordering, exact item/version/viewable identities, receipt expiry/session isolation/access revocation, trusted-import provenance, semantic deduplication, unknown units/null values, identifier fallbacks, unsafe keys/collisions, extraction limits and denied/unready derivatives. These establish local implementation behavior, not Autodesk customer authorization. HTTP boundary tests are in `tests/model-data-http.test.ts`.

Embedded Viewer and element highlighting are **not implemented or live verified**. The source browser states the dependency and offers a native Autodesk model link only when APS supplies an HTTPS URL on an allowlisted Autodesk host. A qualified, authenticated SVF/SVF2 derivative and WebSocket proxy with per-model/version authorization and restricted upstream paths is required to preserve server-only tokens. The official [Viewer proxy approach](https://aps.autodesk.com/blog/proxying-aps-viewer) is the starting contract, not evidence of a completed Viewer integration.

## Live evidence and remaining gates

On 2026-10-19 the root implementation ran one live app-credential check: `POST /authentication/v2/token`, `grant_type=client_credentials`, scope `data:read`. APS returned **HTTP 200**, `token_type: Bearer`, and `expires_in: 3599`; the response did not include a scope field. The token was discarded. No project request or remote data write was made in this probe. **App credentials verified only.**

**End-user consent and project-bearing Forma hub access remain unverified.** The successful app-only token exchange does not establish user identity, membership, project access, capture/media access, or write permission.

Before describing the integration as project tested:

1. Start in live mode and complete Autodesk consent in the browser. Confirm that the configured ID is the intended Forma data hub; use the actual project hub ID if it differs from the supplied Developer Hub ID.
2. Read the intended user's projects successfully; record only sanitized project IDs/names and the user's role with permission to retain them. Check a denied user/project case separately.
3. Exercise pagination on an authorized multipage result and verify rate-limit/region behavior against the current full endpoint reference. No partial lists should be presented as complete.
4. Exercise the implemented folder/item/version browser and property extraction against an authorized representative model. Confirm View + Download access where required, actual format eligibility, ready derivatives, expected category/property coverage, source units and stable identities. Check denied, expired, deleted and unready sources; retain no partial extract as complete.
5. Qualify embedded viewing/highlighting separately through the server-only proxy described above. Photos/capture reads, Issue/RFI writes, attachments, reconstruction and quantity certification remain separate unverified capabilities; the new adapter does not implement them.

The [handoff capability register](handoff/docs/04-api-capability-register.md) retains the broader research and later-phase gates. Selecting APIs in Developer Hub is not evidence of any of those project-specific permissions.
