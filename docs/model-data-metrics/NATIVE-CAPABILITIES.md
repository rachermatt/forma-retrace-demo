# Native Autodesk capabilities and development boundaries

Reviewed: **2026-11-04**. This is a documentation-based assessment, not a customer validation or an implemented model-data feature. The proposed outcome is reusable, trustworthy For-Record/As-Built element information across authorized projects, including properties as well as quantities. Native product workflows should be tested before equivalent custom interfaces are commissioned.

“Not established by the reviewed documentation” means a dependency remains to be tested; it does not mean the capability or an API is absent. Product UI support, an available API, subscription entitlement and demonstrated access to a particular project are separate evidence.

## Classification transition: avoid a two-system assumption

Autodesk’s change notice states that projects created from October 15, 2026 use the new Forma Classifications model with up to five classifications per item. Existing projects start conversion November 30; deprecated-field support ends January 29, 2027. Dates are subject to change, and mixed project states can coexist. Inspect `takeoff.settings.forma_classifications` or `estimates.settings.forma_classifications` per project rather than inferring state from account age. [Change notice](https://help.autodesk.com/cloudhelp/ENU/Docs-Insight/files/data-connector/Data_Connector_Change_Notice.html).

In Data Connector, resolve `classification1_node_id` through `classification5_node_id` through the shared classifications service. Numbered slots are not stable classification-system identities. Converted legacy columns may be empty without an error; do not interpret that as unclassified scope or zero quantity. Follow the documented quantity-definition joins and changed sheet-version references. This assessment therefore does not characterize multi-classification as a wholly missing native feature. [Same change notice](https://help.autodesk.com/cloudhelp/ENU/Docs-Insight/files/data-connector/Data_Connector_Change_Notice.html).

## Room semantics and proof-of-fit priorities

Architectural rooms and MEP spaces are not interchangeable. Revit documents that a space’s linked-room identity is based on relative location, not a link to a particular room ID; changes can leave spaces ambiguous or unenclosed. [Room/space behavior](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-ArchDesign/files/GUID-C58613B6-1792-4273-8F92-0309ABBF2CE8.htm). Native room association should therefore be evaluated with linked architectural, MEP and structural models, including missing rooms, phase differences and coordinate changes.

Recommended first trials are: a native Takeoff multi-output example; Datum information requirements and validation; Tandem metadata and room import; and a Data Connector extraction with the tenant’s actual classification schema. Record the source/version, output fields, unresolved cases and permission behavior for each trial. Verify units and quantity meaning independently of whether a value can be exported.

The likely custom layer is orchestration and a permission-aware derived index: approved For-Record/As-Built source selection, category-specific property profiles, normalization, rule/run provenance, exception handling and reusable cross-project queries. This is a design recommendation, not a verified absence of native capabilities. Favor deterministic approved processing and exception review; “minimal human interaction” must not silently become unverified model interpretation or automatic approval.

Representative model access, data standards, acceptance tolerances, API contracts and licensing remain customer validation dependencies. No live customer models, unattended classification run, quantity-accuracy result or production integration has been demonstrated by this assessment.
