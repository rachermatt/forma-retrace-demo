# APS options for model data and metrics

Verification date: **November 4, 2026**. This register distinguishes documented Autodesk capabilities from adapters that would require development and qualification. Documentation verification does not establish customer entitlement, project access, model eligibility, production readiness or successful integration. It does not implement the model-data workstream. The existing evidence-review workflow and its security boundaries remain the starting point; see [APS verification](../APS-VERIFICATION.md).

## Access and extraction options

| Option | Documented capability | Qualification and application responsibility |
| --- | --- | --- |
| **Data Management API** | Hubs, projects, folders, items and versions provide the source hierarchy. Read requests require `data:read`; supported account access depends on the authentication and integration context. [API basics](https://aps.autodesk.com/en/docs/data/v2/overview/basics) | Browse authorized folders and exact model versions; preserve source IDs, region and version provenance. Do not substitute application-owned storage for the project's system of record. |
| **AEC Data Model** | GraphQL access reaches granular elements and parameters. Autodesk's current workflow description covers Revit 2024+ models hosted in Forma. [API overview](https://aps.autodesk.com/developer/overview/aec-data-model-api), [April 2026 workflow](https://www.autodesk.com/blogs/construction/from-files-to-data-unlocking-data-driven-aec-workflows-with-the-aec-data-model-api/) | Verify extraction eligibility, category coverage, requested properties, units, pagination and source-version mapping on representative models. Do not assume older files or every authoring parameter are available. |
| **Model Properties API** | SVF2 indexing includes properties, identifiers and viewable bounding boxes; differences can include properties and geometry. Autodesk documents user-context authentication, View+Download folder permission, format restrictions and an index cache lifetime. [Official description](https://aps.autodesk.com/blog/bim-360acc-model-properties-api) | Test actual file eligibility and supported version comparisons. The service index is an extraction aid; the application's retained, governed dataset needs its own lifecycle and provenance. |
| **Model Derivative** | Object hierarchy, metadata and selected-property queries are available; filtering and pagination reduce unnecessary responses. [Metadata extraction](https://aps.autodesk.com/en/docs/model-derivative/v2/developers_guide/basics/metadata_extraction) | Qualify each source format and derivative/viewable. Retain missing properties as missing. Handle processing availability, quotas, retries and partial responses; do not equate a translated property with an approved estimating basis. |

Recommended adapter selection is per source model/version, not a universal promise that one API returns all information. Establish a small extraction proof before building the cross-project catalogue. Retain raw property values, source definitions and units alongside normalized values, with the transformation version and validation result. Select initial property profiles by category; expand them after measured coverage and processing results.

## Identity, federation and geometry

Viewer `dbId` values can change between versions. Autodesk recommends external IDs for associations outside the Viewer. Persist the source project, file/model, exact version and external element identity; retain AEC element-group/version and viewable identifiers where applicable. Treat `dbId` as a version-specific rendering lookup. [External IDs and dbIds](https://aps.autodesk.com/blog/get-dbid-externalid)

Viewer APIs expose instance world transforms and world bounds. Autodesk's multi-model alignment guidance also explains placement transforms and global offsets. Architectural rooms and engineering elements must therefore be compared in an explicitly validated common coordinate system, preserving units and each linked-model instance's identity and transform. [World bounds and transforms](https://aps.autodesk.com/en/docs/viewer/v7/reference/Scene/InstanceCollection3D), [multi-model alignment](https://aps.autodesk.com/blog/managing-multi-model-alignment-aps-viewer)

Bounding-box overlap is a candidate-generation method, not proof of room containment, adjacency, net volume or selected formwork surface. This is an engineering conclusion from the representation: Autodesk's alignment discussion illustrates how axis-aligned bounds can exaggerate a rotated model's footprint. Qualification must cover irregular rooms, openings, boundaries, elements spanning rooms, repeated links and missing rooms/spaces. Preserve an unresolved result when the chosen geometry method cannot support the relationship. [Bounding-box limitations in alignment](https://aps.autodesk.com/blog/managing-multi-model-alignment-aps-viewer)

Do not describe AEC Data Model geometry as categorically unavailable. Autodesk announced a **Geometry Public Beta** exposing element geometry, origins/axes and transformations. Its official SDK sample still identifies beta status and advises against production use without qualification. Evaluate access, supported representations and deployment requirements separately from the initial metadata workstream. [Geometry announcement](https://aps.autodesk.com/blog/access-revit-geometry-aec-data-model-public-beta), [official beta SDK sample](https://github.com/autodesk-platform-services/aps-aecdm-data-sdk-code-sample)

## Interactive access and unattended processing

Autodesk's October 2026 guidance recommends ordinary three-legged OAuth for interactive applications and Secure Service Accounts for unattended jobs. An SSA can obtain user-context access without an interactive person, but must be provisioned and granted appropriate project permissions. This is not a reason to replace signed-in access with an unrestricted application identity. [Authentication choice](https://aps.autodesk.com/blog/3-legged-oauth-vs-secure-service-accounts), [SSA project permissions](https://help.autodesk.com/cloudhelp/ENU/Docs-Admin/files/hub-administration/custom-integrations/Account_Admin_SSA.html)

The ingestion principal and a dataset consumer are different authorization subjects. As an application design requirement, a processing account's ability to read multiple projects must not automatically grant every catalogue user access to their derived records. Decide whether consumers inherit current source permissions or receive a separately authorized published dataset. Define project restrictions, revocation, deleted/archived-source handling, retention, audit and export policy before admitting real project data.

Keep APS credentials and tokens on the server under the existing project rule. Autodesk provides an SVF/SVF2 Viewer proxy pattern that avoids returning an APS token to browser code. Qualify an authenticated proxy with per-model/version authorization and restricted upstream paths; do not implement an open forwarding endpoint. [Viewer proxy approach](https://aps.autodesk.com/blog/proxying-aps-viewer)

## Changes, processing and consumption

Webhooks and AEC Data Model differences can support change-driven ingestion. Autodesk explicitly advises proving that each desired source change appears in a diff, and handling extraction lag. Use a durable queue, idempotent jobs, exact source/configuration baselines, retries and explicit failed/partial states. A notification is a trigger to investigate, not a completed extraction or approved dataset. [October 2026 change-processing workflow](https://aps.autodesk.com/blog/build-your-own-webhooks-revit-cloud-model-changes)

AEC Data Model GraphQL subscriptions are also documented in **Public Beta**, with a current limitation: events are emitted when extraction completes successfully. They do not alone provide failure detection or full job orchestration. Keep the event adapter optional until access and behavior are qualified. [Subscriptions announcement](https://aps.autodesk.com/blog/build-event-driven-workflows-aec-data-model-graphql-subscriptions)

AEC Data Model Data Out pricing took effect October 6, 2026. Included capacity depends on qualifying subscriptions and APS application/team placement. An external historical database therefore needs a verified usage/budget plan and consumption visibility; do not assume unlimited free bulk extraction. No price or customer allowance is quoted here. [Current commercial explanation](https://aps.autodesk.com/blog/data-model-apis-included-subscriptions-plus-flexible-ways-scale)

## Datum as a reuse decision

Autodesk Datum is a commercial product candidate, not merely a future announcement. Its product page describes browser-based asset-information management, multiple concurrent standards, corporate/project class libraries, classification variants and mappings, with subscription information through sales. Test these capabilities against the governance requirements before rebuilding equivalent functions. [Datum product information](https://www.autodesk.com/products/datum/overview)

The APS Datum overview confirms JSON REST read/write, import/export and automation capabilities for Datum and Datum Class Library. Detailed API documentation requires signing into those products. Exact endpoints, customer entitlement, estimating assignments, quantity semantics and cross-project reuse behavior remain unverified here. Do not infer Datum entitlement from a Docs subscription or declare the complete use case solved by the product overview. Obtain authorized product access and run a proof of fit. [Datum API overview](https://aps.autodesk.com/developer/overview/autodesk-datum-api)

The proposed development gap is a governed orchestration and derived-data layer: versioned many-to-many classification assignments, category-specific property profiles, approved quantity bases, exception handling, reproducible publication and authorized historical reuse. Start with eligible model metadata and explicit rules; qualify federated room geometry and selected-surface measurement as separate milestones.
