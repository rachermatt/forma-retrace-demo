# Model access and format verification

Updated November 4, 2026. The application now implements an authorized, read-only model-source browser and Model Derivative property import. Its local contract tests pass; live customer authorization and model access have not been demonstrated. No Viewer token endpoint or external write adapter is provided.

## What is verified

- Server-side confidential OAuth, project discovery and the new [model-source adapter](../server/aps-models.ts) are implemented. In live mode, a consenting user can browse the configured hub's permitted projects, top folders, folder contents, model items, exact versions and processed 3D metadata viewables. Mocked tests verify these contracts and boundaries; they do not prove customer access.
- A selected version's properties can be prepared server-side and imported using a short-lived, session-bound receipt into the separate local Model Data & Metrics library. Import rechecks source access and retains project, model item, exact version, derivative/viewable, element identifiers and extraction time. Browser-authored JSON cannot claim verified APS provenance.
- The imported properties retain raw scalar values; missing parameter units remain unknown. This adapter does not extract geometry, room solids, source transforms or measured surfaces. File-format labels come from source filenames; format eligibility still requires a representative source exercise. For-Record/As-Built designation is unverified until a separate basis is recorded.
- Source external IDs are retained when provided. If absent, the adapter explicitly marks a version/viewable/object-ID reference; it must not be treated as a global or cross-version element identity.
- The existing evidence-review source model remains a **three-element reference fixture**, not an RVT/IFC/SVF/SVF2 file. Its drawings and captures are SVG illustrations. The separate model-data demonstration contains authored property and bounding-box fixtures, not customer BIM geometry.
- Local photograph workspace model/element identifiers are manually supplied references and explicitly unverified. Selecting an identifier or drawing an image rectangle does not validate geometric registration.
- Actual customer model format, version URN, region, successful derivative and per-user read permissions have **not** been established. No representative, authorized BIM source has been exercised. Existing findings and model references are not moved or reassociated by a metadata import.

## Exact blocker

For live qualification, we need the intended user's completed consent, a confirmed project-bearing hub and project, appropriate folder/model access including View + Download where required, a ready 3D derivative for the exact source version, and authorization to retain its extracted properties. The previously supplied hub may be an application-management Developer Hub; app credential validation does not prove it contains project data. No credential/token value is recorded here. Successful sign-in by itself still leaves model/capture/write access unverified.

Embedded model viewing and element highlighting remain a separate dependency: qualify a server-side SVF/SVF2 derivative and WebSocket proxy with per-model/version authorization, strict upstream allowlists and no APS tokens sent to browser code. The source browser reports this limitation. If APS supplies an HTTPS model-view link on an allowlisted Autodesk host, the interface offers that native viewer link; it does not claim an embedded Viewer or highlighting demonstration.

## Documented integration checks before enabling a real model

1. Use the [Model Derivative reference](https://aps.autodesk.com/en/docs/model-derivative/v2/reference/) to check `GET /formats` for the actual input format. The source adapter already checks the selected version's manifest readiness and metadata views before property extraction, but those checks still need a live authorized source exercise. A generic supported-format list is not a successful project translation.
2. Autodesk's [online model preparation guide](https://aps.autodesk.com/en/docs/model-derivative/v2/developers_guide/basics/preperation/) describes SVF/SVF2 viewing and identifies external IDs as the persistent source-object linkage; per-translation dbIds can change. Preserve model version with each finding.
3. The [OAuth scope guide](https://aps.autodesk.com/en/docs/oauth/v2/overview%20%20/scopes) describes the restricted `viewables:read` Viewer pattern, which normally passes a token to browser JavaScript. The present product rule keeps credentials and tokens on the server. Autodesk's [Viewer proxy pattern](https://aps.autodesk.com/blog/proxying-aps-viewer) supports an implementation without browser APS tokens; its authorization, derivative paths and WebSocket behavior must be qualified before enabling embedded viewing. The implemented source browser continues to request only `data:read` and exposes no APS tokens.
4. Validate actual user/model permissions, region, source-version mapping, selected-element highlighting and denied/expired/missing-model behavior before enabling viewing. Translation jobs are external operations and require a verified, explicitly authorized workflow.
5. Verify Issue and RFI endpoints and attachment flows separately. The official [Issues tutorial](https://get-started.aps.autodesk.com/tutorials/acc-issues/issues) is a contract starting point, not proof of this project's permission or attachment success. No external submission endpoint is implemented here.

The existing human-reviewed evidence workflow is unchanged: fixture and manually configured model references remain labeled, locally imported photographs are not represented as APS captures, and manual plan placement remains an association with explicit unverified alignment. Importing actual model metadata does not verify field registration, installation, acceptance or quantities. See [APS verification](APS-VERIFICATION.md) for tests and [model-data APS options](model-data-metrics/APS-OPTIONS.md) for the broader qualification register.
